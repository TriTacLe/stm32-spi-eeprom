% --- Section 5: the fault ----------------------------------------------------
% The four table columns. Keep each to a phrase; the narrative goes below.
\newcommand{\mFaultExpected}{MOSI stable across the rising SCK edge}
\newcommand{\mFaultObserved}{MOSI changing on the rising SCK edge}
\newcommand{\mFaultCause}{SPI2\_CR1 bit 0, CPHA, set to 1}
\newcommand{\mFaultCorrection}{CPHA returned to 0}

% The diagnosis in prose: the first meaningful difference between the two
% captures, and why the corrected configuration now satisfies the device
% electrically. This is where the marks are.
\newcommand{\mFaultNarrative}{The fault case writes to the peripheral at 0x40003800, which is SPI2, and sets bit 0 of its control register. That bit is CPHA, so the configuration becomes CPOL 0 with CPHA 1 rather than the mode 0 the device requires. The hook clears SPE before it writes the field and restores it afterwards, which is what makes the new mode take effect rather than be ignored on an already enabled peripheral.

The first meaningful difference between the two captures is where MOSI moves relative to SCK. Correctly configured, the STM32 changes MOSI on the falling edge, so the line has settled by the time the rising edge arrives. With CPHA set, the STM32 changes MOSI on the rising edge instead. The EEPROM is still a mode 0 device and still samples on the rising edge, so the line is moving at the exact instant it is read.

Electrically this violates the setup and hold requirement around the sampling edge: the device may capture the previous bit, the new bit, or a level that is neither while the line is in transition. Returning CPHA to 0 restores the falling-edge update, MOSI is stable before each rising edge, and the transaction completes correctly.}

% --- Section 6: the state machine --------------------------------------------

% One complete run through the state machine.
\newcommand{\mFsmResult}{One press of PA0 ran the whole transaction through the state machine. The location held \texttt{0xFF} beforehand, an erased cell, so the change on the outputs is the write itself. After the press the status register read \texttt{0x00}, with WEL cleared by the device on completion; the busy state polled for 4\,ms before RDY went low, against the 5\,ms maximum the datasheet allows; the read-back returned \texttt{0x3D}; and the comparison passed, leaving the machine in its succeeded state. \texttt{GPIOB\_ODR} read \texttt{0x183D} at that point, so PB0 to PB7 carried \texttt{00111101} and the green status LED was lit with the red one off.}
